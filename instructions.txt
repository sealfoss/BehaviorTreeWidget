Goal: Develop a qt widget used to build and execute behavior trees graphically
in python using the py_trees library - the BehaviorTreeWidget class.

It is expected this widget will developed using the python virtual environment
located in .venv.

The BehaviorTreeWidget should be a tabbed widget. One tab should view the 
behavior tree. The other tab should view the black board.

The behavior tree view tab UI is defined in BehaviorTreeView.ui and contains
two frames: FrameView and FrameExecution

    FrameView is intended to house the generated graphical behavior tree.
    For now, the BehaviorTreeWidget class will support three primary 
    node widget types each of which have defined .ui files.
        1. RootNode
            a. The first node executed.
            b. Has no parent. 
            c. Can be a sequence or selector node. 
        2. CompositeNode
            a. A sequence or selector node.
            b. Has children and a parent.
        3. LeafNode
            a. Primary logic execution node.
            b. Has no children.
            c. Derived classes override the OnRun function.

    The base NodeWidget has been partially defined for example purposes 
    featuring an OnRun function meant to be called when that node is executed.
    The intention is for custom LeafNodesWidgets to be derived containing
    the bulk of the end user developers functionality for the tree. Each
    node has a _title member defining the title of that node, typically its 
    type ("Sequence", "Selector", "Root"). This value will be reflected in the
    node's ui Title QLabel text. The Status QLable will denote one of the
    following possible states for that node:
        1. "Ready" - this node has not yet been run.
        2. "Running" - this node is currently running.
        3. "Succeeded" - the node's operation succeeded.
        4. "Failed" - the node's operation failed.

    All nodes except the Root node have a ParentConnection QLabel component.
    If no connection to a parent is made, this QLabel should be colored red.
    If a connection is being placed, this QLabel should be colored green.
    If a connection has been made, the QLabel should be colored blue.
    All nodes except leaf nodes will have the ChildConnections QLabel.
    The ChildConnections QLabel should operate in the same way as the 
    ParentConnectionQLabel.
    
    Click and drag shall be the method of connecting the ChildConnection 
    QLabel of one node to a ParentConnection QLabel of another node, or vice 
    versa. A ChildConnections QLable must be connected to the 
    ParentConnection QLabel of another node. A ParentConnection QLabel must
    be connected only to the ChildConnections QLabel of another node.
    
    When a connection is being made and the mouse is still clicked, a 
    line should be drawn from the clicked QLabel to the cursor. While the
    cursor is not hovering over a compatible QLabel, it should be red. While
    the cursor is hovering over a compatible QLabel, it should be green.
    and when the mouse has been released over a compatible QLabel and the
    connection is made, the line should remain and be colored blue. If no
    connection is made, the line should disappear.

    Clicking on the connection line between nodes selects it. Clicking 
    anywhere else after connection line has been selected deselects it.
    Selected connection lines go back to being colored green. Hitting the
    delete key while a connection line is selected deletes the connection
    between those two nodes. Creating a connection between two nodes where
    the child node already has a parent deletes the connection to the original
    parent node and replaces it with the connection to the new parent.

    Leaf Nodes may contain data known as fields. Fields can be strings, ints,
    floats, bools or lists. Values for these fields are stored by name (key) 
    in the _fields dict of the NodeWidget class. If any fields are preset in 
    a given leaf node's _fields dict, they should be denoted in
    the widget's Fields ListView component paired with a LineEdit containing
    the key (name) of that field. Next to the value name, int values should be 
    represented with SpinBoxes, float values with DoubleSpinBoxes, strings 
    with LineEdits, bool values with check boxes, and lists with ComboBoxes 
    enumerating the string representation of each value contained in the list.
    Leaf node UIs should be resized appropriatly to accompodate the contained
    number of fields. Changes to the fields in the behavior tree UI should
    be immediately reflected in the _fields member of that NodeWidget. If
    a given node has no fields, the FrameFields member of the UI should be
    hidden and the widget should be resized to accomodate this.


    FrameExecution has buttons to control execution of the behavior tree.
        1. Execute - begins execution.
        2. Pause - halts execution.
        3. Stop - halts execution and resets the tree to its initial state.
        4. Reset - Resets the tree to its initial state without halting.
        5. Configure - Opens a window to configure any tree options.
        6. Save - Save the current tree to .json file through dialoge box.
        7. Load - Load a behavior tree .json file through dialoge box.
        8. New - Create a new behavior tree stored in a .json file located via 
        dialogue box.
    
    

The black board view tab UI is defined in BlackBoardEntries.ui.
The QScrollArea EntryList is to display the values added to the blackboard.
Widgets have defined for String (StringEntry.ui), Integer (IntegerEntry.ui), 
Float (FloatEntry.ui), and List (ListEntry.ui) entries in the 
blackboard. Each entry added must be named via the ValueName LineEdit.
Each entry value is located in the Value sub widget. For IntegerEntry, Value
is a spin box. For FloatEntry Value is a double spin box. For StringEntry
Value is a LineEdit. 

Each entry made in the black board should be available and setable by its name 
through functions in the BehaviorTreeWidget class following this pattern:  
GetEntry(self, name: str) and  SetEntry(self, value, name: str). 
Each entry has a Select checkbox to denote that it has or has not been 
selected. The BlackBoardView has a SelectAll checkbox used to select or 
deselect all entries. The AddEntry button will add an entry to the EntryList 
of the type designated by the ComboBox EntryType through a popup dialoge box.
The RemoveEntries button will remove all selected entries in the EntryList.

Clicking and dragging on the BehaviorTreeView outside of any node should pan
the view up/down, left/right. Clicking and dragging on a node outside of its
parent/child connection label should move that node around in the 
BehaviorTreeView. Right clicking a node should provide a pop up to delete it.
Right clicking an empty party of the BehaviorTreeView should provide a pop
up enumerating the types of nodes available, allowing the user to add one of
them at that point in the BehaviorTreeView.

Leverage py_trees as much as you can for the underlying behavior tree 
execution. The intent of this ui is simply to make utilizing py_trees easier.
This will be a starting point. I simply want root nodes, selection nodes,
sequence nodes, and custom leaf nodes. The tree should start with a root node
already in place. Until a tree is loaded or created, the BehaviorTreeView 
should be disabled. When a tree is loaded or created, the name of the 
file containing that tree should be written to the title bar in the format:
f"Behavior Tree - {filename}"
